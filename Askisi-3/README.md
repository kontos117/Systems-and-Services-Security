<h3>Κωνσταντίνος Κοντός 2022030116<br>Χρήστος Καδάς 2022030076</h3> <h1>Access Control Logging με χρήση LD_PRELOAD</h1> <h2>Περιγραφή</h2> <p> Η εργασία υλοποιεί ένα σύστημα καταγραφής και ανάλυσης ενεργειών πρόσβασης σε αρχεία, βασισμένο στη μέθοδο παρεμβολής συναρτήσεων μέσω <b>LD_PRELOAD</b>. Το σύστημα αποτελείται από τρία βασικά μέρη: </p> <ul> <li><b>audit_logger.so</b> - δυναμική βιβλιοθήκη που παρακολουθεί fopen, fwrite, fclose</li> <li><b>audit_monitor</b> - πρόγραμμα ανάλυσης του αρχείου καταγραφής</li> <li><b>test_audit</b> - πρόγραμμα δοκιμών που επιβεβαιώνει τη σωστή λειτουργία του συστήματος</li> </ul> <br>
<h2>Λειτουργία Συστήματος</h2> <h3>1. audit_logger.so</h3> <p> Το logger παρεμβάλλεται στις συναρτήσεις <b>fopen</b>, <b>fwrite</b> και <b>fclose</b>. Κάθε ενέργεια καταγράφεται σε αρχείο log με τα παρακάτω στοιχεία: </p>

UID χρήστη

PID διεργασίας

Απόλυτο path αρχείου (με χρήση realpath)

Ημερομηνία και ώρα

OP (1=fopen, 2=fwrite, 3=fclose)

DENIED (0=επιτυχία, 1=αποτυχία)

SHA-256 hash του περιεχομένου του αρχείου

<p> Για την αποφυγή αναδρομής όταν υπολογίζεται το hash, χρησιμοποιούνται οι πραγματικές συναρτήσεις fopen/read από το libc, όχι οι hooked. </p> <p> Το αρχείο καταγραφής αποθηκεύεται στο:<br> <b>/tmp/access_audit.log</b> και δημιουργείται αυτόματα αν δεν υπάρχει. </p> <p> Αν μια ενέργεια αποτύχει (π.χ. ανοίγουμε αρχείο χωρίς δικαιώματα), τότε καταγράφεται με <b>DENIED=1</b>. </p> <br>
<h3>2. audit_monitor</h3> <p>Το audit_monitor αναλύει το αρχείο καταγραφής και λειτουργεί σε δύο modes:</p> <h4> -s (Suspicious Users Mode)</h4> <p> Εντοπίζει χρήστες που έχουν περισσότερες από 5 αποτυχημένες (DENIED) προσβάσεις σε διαφορετικά αρχεία. Αν υπάρχουν, χαρακτηρίζονται ως ύποπτοι. </p> <h4> -i &lt;filename&gt; (Information Mode)</h4> <p>Παρουσιάζει όλες τις ενέργειες που έχουν καταγραφεί για ένα συγκεκριμένο αρχείο.</p> <p><b>Υπολογίζει επίσης:</b></p>

Πόσες ενέργειες OP=2 (fwrite) έγιναν

Πόσα διαφορετικά hashes εμφανίστηκαν => δηλαδή πόσες πραγματικές τροποποιήσεις έγιναν στο αρχείο

<p> Παράδειγμα λογικής unique modifications: Αν οι διαδοχικές εγγραφές παράγουν hashes A => B => A, τότε υπάρχουν 2 μοναδικές αλλαγές. </p> <br>
<h3>3. test_audit</h3> <p> Το πρόγραμμα δοκιμών δημιουργεί ένα σύνολο από αρχεία και εκτελεί ενέργειες με στόχο να επαληθεύσει όλες τις λειτουργίες του logger και του monitor. </p>

Κάνει τα εξής:

Δημιουργεί 9 αρχεία

Σε μερικά κάνει πολλαπλά fwrite, προκαλώντας αλλαγές hash

Κάποια τα αφήνει χωρίς αλλαγές ώστε να ελέγχουμε σταθερό hash

Προκαλεί επίτηδες 6 denied προσβάσεις σε διαφορετικά αρχεία
=> ώστε το audit_monitor -s να εντοπίζει ύποπτο χρήστη

<p> Επιπλέον, μέσα στο log υπάρχει κάθε φορά μια κλήση fclose σε αδιάφορο system file (όπως /etc/ssl/openssl.cnf), κοινή για όλα τα συστήματα, η οποία δεν επηρεάζει την αξιολόγηση. </p> <br>
<h2>Τεχνικές Λεπτομέρειες και Παραδοχές</h2> <h3>STEP 2</h3>

OP=1 => πρώτη πρόσβαση / fopen

OP=2 => εγγραφή / write => modification++

Unique modifications = διαφορετικά hashes μετά από fwrite

DENIED=1 όταν μια λειτουργία δεν επιτρέπεται

Όλα τα logs έχουν μια τυπική fclose σε system file => δεν επηρεάζει τα αποτελέσματα

<br> <h3>STEP 3</h3>

Δημιουργούνται 9 αρχεία

Σε μερικά γίνονται πολλαπλές εγγραφές ώστε να αλλάζουν τα hashes

Αρχεία που δημιουργούνται αλλά δεν τροποποιούνται εμφανίζουν σταθερό hash στο log
